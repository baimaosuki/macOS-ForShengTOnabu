# NABU 八核启动修复（2026-11-13）

该候选将 NABU 的八个 CPU 节点、PSCI 启动、GICv3 SGI 和原版 XNU CPU 注册完成路径配对。
主机检查已通过；新内核仍需 CI 编译和实机启动，不能把这份配置视为八核实机上线记录。

## 原先为何只有一个核

基线 `43224981411` 的设备树由 `make_nabu_adt()` 只生成 `cpu@0`，启动参数为 `cpus=1`。
只改为 `cpus=8` 不会创建不存在的 CPU 节点，而且 ArmCpu 的副核匹配仍需 `sheng-smp=1`。
旧 `native_smp.configure(..., board='nabu')` 漏加这一开关，并核对了 SHENG 的补丁和已移动的 timer 补丁路径。

实际 ARM64 NABU 复位入口原先使用 `MPIDR & 0xff`；SM8150 的核心 affinity 是
`0,0x100,0x200,0x300,0x400,0x500,0x600,0x700`。这会让所有副核选中 CPU0 的数据，
而不是自己的 `cpu_data`。新增 NABU 专用补丁在 reset-vector 查表时保留低 16 位。
没有开启 `HAS_CLUSTER`：它还控制 Apple 的硬件集群和节能寄存器路径，不能仅为修正 affinity 打开。

另一个缺口是 ArmCpu 注册结束后没有调用 `ml_cpu_init_completed()`。
原版 XNU 的 `ml_processor_register()` 在 `!USE_APPLEARMSMP` 目标中已经执行 `processor_boot()`；
驱动必须在所有成功注册返回后调用原版完成函数，让调度器等待各核首次启动并完成自身记账。
补丁按采纳的拓扑核数累计成功返回，检查 PSCI 和失败状态后仅调用一次，随后发布
`IOAllCPUInitialized`。没有写 `pcs_init_completed`，没有删除 sleep panic 或启动完成检查。
单核也要经过同一条真实完成路径。PSCI 失败或缺核不会伪造成功。

## 配套硬件资源与配置

- `/psci/method = "smc"`，调用 64 位 `CPU_ON` 函数 `0xc4000003`，入口仍为 XNU 的物理 `LowResetVectorBase`。
- GICD `0x17a00000`，GICR `0x17a60000`，redistributor 区域 `0x100000`，stride `0x20000`；按 `GICR_TYPER` affinity 选择每核 frame。
- 沿用设备启动已使用的 virtual timer INTID 19 和 `ICC_SGI1R_EL1` SGI0 IPI；开启 `armcpu-self-ipi=1`。
- ADT CPU0 为 `running`，副核为 `stopped`；CPU0–3 为 Cortex-A55，CPU4–7 为 Cortex-A76，`reg = logical_id << 8`。
- 继续使用 generic SMP scheduler，不声明 Apple 的 E/P 集群电源管理；保留 `/defaults/sleep-disabled=1`。

硬件描述对照 `platform/nabu/macos26/dts/sm8150.dtsi` 和 iOS NABU 参考包
`.work/ios16-gpu224-reference/deployment/GPU224-Deployment-Kit/tools/make_nabu_adt.py`。
当前修复不证明系统休眠恢复、CPU 热插拔、逐核 DVFS 或调度性能已经可用。

打包调用 `make_nabu_adt(..., cpu_count=8)`，同时通过
`native_smp.configure(build, 8, graphics, 原cpus1参数, board='nabu')` 生成启动参数。
它要求本次构建记录里的组件补丁哈希、真实 SGI 指令检查和 `nabu_smp_source` 审计。
`assemble_nabu_desktop_candidate.py` 提供 `--cpus 8 --kernel-build build.json`，
也保留 `--cpus 2`、`--cpus 4` 与单核配置供设备定位使用。

## 验证与设备判定

`tests/test_nabu_smp.py` 对固定 UniXNU 与 XNU 源码实际应用整套组件及复位补丁，
把实际注册 barrier 函数编译成主机 C++ 程序运行：检查 1/2/4/8 核最后登记前不完成、
PSCI/初始化失败不完成，以及并发登记只发布一次完成。
它也解析 1/2/4/8 核生成 ADT，逐核检查 affinity、类型和启动状态。
现有 SGI Mach-O 汇编检查和逐核日志 formatter 的 SHENG/NABU 主机编译测试通过。
这些检查不替代完整内核链接与设备运行。

## 八核实机失败及冷启动入口修复

构建 `43278284580`、UUID `EB021EFB-9868-39FD-9E9D-C8135719D07D` 的八核候选
在设备上触发 `cpu 1 failed to boot for the first time, waited 1 seconds`。
实际内核符号与字节把 caller `0xfffffe00073e2ad0` 对应到
`processor_wait_for_start+0x1b4`。这证明 CPU1 没有完成首次调度器启动，
此前主机检查不能作为八核实机通过的证据。

同一镜像 `reset_vector+0x1c` 的机器指令确实为 `AND x0,x15,#0xffff`，
所以 Affinity1 修复已被编入；不能把本次故障归因于旧的低 8 位掩码。
照片中的 ELR `0xfffffe00075a17e8` 是 `machine_idle+0x104` 的
`LDP x29,x30,[sp,#0x30]`，不是副核复位的自旋位置。
该读指令也不符合同时显示的 ESR `0x9600004f` 的写权限故障方向，
这组异常寄存器不能单独确定 CPU1 卡点。

随后核对固定 XNU 和 iOS NABU 参考中的实际启动设计，补齐两项具体契约：

- `nabu_secondary_entry` 是独立、页对齐且无栈的物理入口。它先读取 `CurrentEL`；
  EL1 进入原版 reset vector，只有 EL2 分支才设置 AArch64 EL1、timer、GIC SRE 和
  无 stage-2 翻译状态，并通过 `ERET` 进入 EL1h。它没有假定所有固件都从 EL2 返回。
- `cpu_start` 保留原版对 `CpuDataEntries` 和目标 `cpu_data` 的清理，另外将
  `cpu_ttep`、整个 bootstrap 表池及实际 kernel table 的有效下级表发布到 PoC。
  表遍历按 L1/L2/L3 层次清理子表后清理父表，叶和块映射不会按数据地址继续递归。

`ArmCpu::startCPU` 改用新入口，并按 `nabu_secondary_entry_end` 的实际边界清理完整入口和
异常向量，避免仅覆盖旧 reset 页。每核独占 64 字节冷启动记录包含阶段、入口 EL、
MPIDR，以及早期故障的 ESR/ELR/FAR 和故障 EL。读取前失效该行，避免启动核缓存的旧零值
遮住 MMU-off 副核写到 PoC 的状态。CPU_ON 前后、进入 `initCPU`、GIC/timer 就绪和最终注册
barrier 前均立即 `kprintf`；不会在 IRQ 屏蔽的 `initCPU` 中调用带中断状态断言的 `IOLog`。
原版一秒等待和失败 panic 均保留。

新增 `test_nabu_secondary_entry.py` 将真实补丁后的入口指令编译并链接为 ARM64 Mach-O，
用 Unicorn 运行非安全 EL1/EL2 × CPU1/CPU7 四个组合，验证到达原 reset vector、最终 EL1h、
无栈使用和正确的每核入口记录。GIC SRE 寄存器由测试模型提供，其他相关系统指令实际执行；
这不模拟设备的 PSCI 固件、缓存一致性或 GIC 中断交付。另把实际 `cpu.c` 表发布函数编译为
主机程序，验证清理 L3→L2→L1 且不解引用块或叶数据。

该补齐尚未完成新内核实机验证，也尚不能确定前述两项中的哪一项触发本次设备失败。
下一轮以 CPU_ON 原始返回、入口 EL、冷记录和 `initCPU` 即时日志分辨。

设备上应记录同一内核 UUID 的 `NABU-SMP` 日志，并同时满足：

1. `registered=8 scheduler-init-complete=1`，`secondaries=7`。
2. CPU1–7 `step=7 fail=0 psci=0`，请求和实际 affinity 一致。
3. 工作负载运行后，八核 timer 与 IPI 计数均有实际到达并持续变化。
4. 桌面服务和 WindowServer 保持运行；另行测量真实跨核调度与性能。

若最后核停在 PSCI 或复位入口，保留错误返回和首次 panic，结合逐核日志定位；
不要把配置核数或 `CPU_ON` 返回 0 当作已上线证据。
