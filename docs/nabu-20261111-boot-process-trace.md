# NABU 25F71 selected boot process diagnostics

This diagnostic candidate investigates the repeating mount PID growth. It does not repair the mount loop or change mount, exec, exit, signature, crash or panic decisions. The source baseline is delivered revision `fbff0581e61dd67e5f15fbe703ac3979ac8d0ddf`; patch 18 adds observations alongside the existing watchdog gate and all earlier compatibility/storage fixes.

`assemble_nabu_desktop_candidate.py --trace-boot-processes` requires kernel symbol `_nabu_lifecycle_trace_events` and adds `nabu-boot-proc=1 sheng-stderr-log=1 sheng-stderr-name=boot-filesystems`. The process trace accepts only bootarg value 1. Normal bundles omit these options. DarwinBoot uses a 1024-byte command line and rejects non-ASCII or length over 1023, so the approximately 300-byte diagnostic arguments fit. The stderr selector is implemented separately in process_output.h; it is not a global executable logger.

The `boot-filesystems` stderr selector also requires `nabu-boot-proc=1`. It selects only the six final program names above and maintains independent budgets per target: first eight attempted writes, then a current write at most once per five seconds with a suppressed count. It retains at most 159 bytes per scalar/vector write and inspects at most 16 iovecs, with truncation marked; copyin failures do not consume a budget. Existing write validation, side effects and return values remain with the original write syscall. These selected stderr records can expose the daemon's own error message; they are bounded samples rather than complete output capture.

The exec hook runs in the successful final Mach-O activator immediately after `set_proc_name`, with the activated vnode and kernel-copied argv still present. It therefore observes both posix_spawn and the subsequent exec from xpcproxy into a service. Targets are exact final names `mount`, `mount_apfs`, `fskitd`, `WindowServer`, `diskarbitrationd`, and `cryptexd`. xpcproxy is selected only for exact labels `com.apple.filesystems.fskitd`, `com.apple.WindowServer`, `com.apple.diskarbitrationd`, and `com.apple.security.cryptexd` from the original cached jobs; unrelated proxy labels remain silent.

`NABU-PROC` records contain monotonic kernel nanoseconds, PID, process unique ID, exec sequence, exec-time parent PID/name and grandparent PID/name, vnode-derived executable path, argv count and bounded arguments. The path falls back to the kernel-saved exec path on vn_getpath failure, with the error recorded. Up to 24 arguments and 511 formatted bytes are retained, with explicit `argv_truncated=1` when incomplete. Environment variables are excluded. Control characters and bracket delimiters in arguments become `?` to preserve record framing. The top-level mount caller and mount_apfs options/device/mountpoint can thus be correlated with a service's earlier records.

The exit hook runs once in proc_exit after releasing the process lock and selecting its committed p_xstat, before proc_refdrain. It records raw wait status, decoded exit code/signal/core flag, and reason namespace/code/flags. Exec-time ancestry/path/arguments are copied from a 64-slot table keyed by process unique ID, which survives the exec shadow-proc replacement. Exit records repeat this information even if that execution's log was suppressed; a first failed exit therefore retains its own parameters. Entries clear on exit or an unrelated later exec, preventing PID reuse from linking unrelated processes. If more than 64 selected processes are concurrently tracked, the oldest record is evicted and the cumulative `evicted` count appears in later output; an evicted process's exit detail can be absent. This capacity limit is explicit and does not exhaust logging after a fixed number of historical events.

Each selected program and each selected proxy label has independent buckets for exec, successful exit and failed/reasoned exit. A bucket emits its first four events, then the current event no more than once per five seconds, reporting `suppressed` events since its previous emission. Successful churn cannot consume the first-failure allowance; late retries and failures continue to produce current samples for the duration of the boot. A typical emitted exec uses two bounded lines, an exit three. This is sampling, not a lossless audit, and exact interleaving across CPUs must be correlated using uid/exec rather than line adjacency. A failure with a changed status during a suppressed interval is represented by the subsequent sampled failure, not guaranteed individually.

Focused validation compiles and executes the actual added C helpers with stand-ins for process lookup, clock, vnode path and allocation. It checks exact filtering, disabled/invalid bootargs, xpcproxy-to-final-image identity, parent/grandparent, retained mount arguments, wait status/reason decoding, successful churn followed by a first failure, and emission of late failures with omission counts. It also checks argument truncation, malformed copied argv, fallback paths, reference balance, assembler opt-in metadata and missing marker rejection. Fresh preparation must apply all 101 source patches and pass the final-activation/committed-exit/recurring-budget source audits. Hardware execution remains required to diagnose the real failure.
