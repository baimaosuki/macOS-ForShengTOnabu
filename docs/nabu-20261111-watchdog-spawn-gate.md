# Explicit watchdogd spawn gate on NABU 25F71

The device running kernel UUID 23C2903D-1282-3290-AD9B-740BD945BC3E still launched watchdogd after the existing launchd disabled-policy writer reported status 0. The exception log gives user PC 0x104434c44; subtracting original watchdogd's BRK address 0x10000cc44 gives aligned slide 0x4428000. This corroborates its actual `unable to lookup watchdog KEXT service` crash after no IOWatchdog service was found. The direct-path-only gate also failed on device kernel UUID 5A958F93-F183-3DC3-95E8-79077057C5CB. Original launchd machine code proves why: PID1 spawns `/usr/libexec/xpcproxy` with `argv[1]` naming `com.apple.watchdogd`; xpcproxy subsequently executes watchdogd. The cause of launchd ignoring the disabled-policy file remains unresolved.

`17-macos-watchdog-spawn-gate.patch` adds a controlled bring-up bypass, selected only by the existing `disable-watchdogd=1` option on NABU desktop builds. At the start of `posix_spawn`, it requires parent PID 1 and either exact pathname `/usr/libexec/watchdogd`, or exact pathname `/usr/libexec/xpcproxy` with exact `argv[1]` label `com.apple.watchdogd`. The proxy route uses a checked 64-bit user pointer read and bounded string copies. It returns ENOENT before allocating spawn state, creating a child, or installing child crash behavior. Invalid pointers, overlong copies, 32-bit proxy parents, unrelated labels, other parent PIDs and other bootarg values follow the original syscall path. This does not intercept PID1's execve, modify Apple binaries/signatures/trust, claim a watchdog service, or change process crash/panic policy.

The existing disabled.plist policy remains present as an advisory request. The global atomic counter `native_owner_watchdog_spawn_blocked` records every rejected attempt; `native_owner_watchdog_proxy_blocked` records proxy rejections. The first rejection prints `owner policy: blocked PID1 watchdogd spawn via xpcproxy before child creation (ENOENT)` (or `directly` for the direct route). Assembly with `--disable-watchdogd` requires both gate counters and the old policy status symbol; an older direct-only kernel cannot silently satisfy the stronger bundle contract.

The original launchd binary has SHA-256 `55228c7ef0f4ea7e702e0a13228dc5227de032d14f365cd80e011f6fd6a35c9d`. Its instructions load the proxy path into x21 at 0x1000203b8, store `argv[0]="xpcproxy"` and the job label pointer at 0x1000203cc, then pass x1=x21 and x4=argv to `_posix_spawnp` at 0x100020568. Libc forwards a pathname containing a slash unchanged to `posix_spawn`. Report: `out/nabu-watchdog-fix2/xpcproxy-spawn-bypass-audit.json`. These are original static instruction observations, not a hardware syscall-register capture.

The original 25F71 launchd spawn-error continuation was executed from 0x10002056c with posix_spawnp returning ENOENT. Its real instructions take normal failure cleanup and error logging, select a retry timer, report errno 2, and return through the normal attempt cleanup. The actual throttle selector 0x100020d00 selects the job's default 10 seconds (the constructor writes 10 at 0x100005bb0/5bb4); this daemon has no throttle override in its original or cached job. Logging, cleanup, dispatch timer setup and notification helpers were explicit stand-ins, so this verifies the branch and selected timer delay, not real scheduling. Report: `out/nabu-watchdog-fix2/launchd-spawn-error-machine-code.json`.

Because no child exists when the kernel returns, there is no watchdogd child exit on which `_PanicOnCrash` or `POSIX_SPAWN_PANIC_ON_SPAWN_FAIL` can act. Launchd can retry and clients of the daemon's Mach services can remain unsatisfied. The implementation intentionally logs the first rejection only; it does not pretend the job was successfully spawned or hide another process's fault. This is an explicit startup bypass, not a fix for the unresolved launchd override discrepancy or a hardware watchdog implementation.
