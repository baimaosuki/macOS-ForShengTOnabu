# Explicit watchdogd spawn gate on NABU 25F71

The device running kernel UUID 23C2903D-1282-3290-AD9B-740BD945BC3E still launched watchdogd after the existing launchd disabled-policy writer reported status 0. The new exception log gives user PC 0x104434c44; subtracting original watchdogd's BRK address 0x10000cc44 gives aligned slide 0x4428000. This corroborates its actual `unable to lookup watchdog KEXT service` crash after no IOWatchdog service was found. The cause of launchd ignoring the override remains unresolved.

`17-macos-watchdog-spawn-gate.patch` adds a controlled bring-up bypass, selected only by the existing `disable-watchdogd=1` option on NABU desktop builds. At the start of `posix_spawn`, it checks parent PID 1 and an exact, bounded user pathname `/usr/libexec/watchdogd`, then returns ENOENT before allocating spawn state, creating a child, or installing child crash behavior. Invalid or overlong user path copies follow the original syscall path and error handling. Other parent PIDs, executables and bootarg values follow the original code. This does not intercept PID1's execve, modify Apple binaries/signatures/trust, claim a watchdog service, or change process crash/panic policy.

The existing disabled.plist policy remains present as an advisory request. The new gate covers an actual executable launch even when launchd imports the job from another path. A global atomic counter `native_owner_watchdog_spawn_blocked` records each rejected attempt, and the first prints `owner policy: blocked PID1 watchdogd spawn before child creation (ENOENT)`. Assembly with `--disable-watchdogd` now requires this separate marker as well as the old policy status symbol; an older kernel cannot silently satisfy the stronger bundle contract.

The original 25F71 launchd spawn-error continuation was executed from 0x10002056c with posix_spawnp returning ENOENT. Its real instructions take normal failure cleanup and error logging, select a retry timer, report errno 2, and return through the normal attempt cleanup. The actual throttle selector 0x100020d00 selects the job's default 10 seconds (the constructor writes 10 at 0x100005bb0/5bb4); this daemon has no throttle override in its original or cached job. Logging, cleanup, dispatch timer setup and notification helpers were explicit stand-ins, so this verifies the branch and selected timer delay, not real scheduling. Report: `out/nabu-watchdog-fix2/launchd-spawn-error-machine-code.json`.

Because no child exists when the kernel returns, there is no watchdogd child exit on which `_PanicOnCrash` or `POSIX_SPAWN_PANIC_ON_SPAWN_FAIL` can act. Launchd can retry and clients of the daemon's Mach services can remain unsatisfied. The implementation intentionally logs the first rejection only; it does not pretend the job was successfully spawned or hide another process's fault. This is an explicit startup bypass, not a fix for the unresolved launchd override discrepancy or a hardware watchdog implementation.

Validation: the extracted actual helper passes opt-in absent/zero/other values, parent PID filtering, exact executable match, neighboring path rejection, copy faults and long path handling, repeated blocks/counter tests. Existing policy writer tests, assembler/memory tests and VM helper tests pass (8 tests total). A fresh complete 101-patch source prepare passes all desktop and arm64e audits; the desktop manifest includes 17 component records. CI and device execution of this revision are still required.

Device acceptance requires the new kernel UUID and paired boot arguments, the first-block log above, continued PID1 activity and progress beyond the earlier watchdog crash time, and no new watchdogd exception 6 at the known BRK PC. The expected replacement evidence is an ENOENT launchd attempt, potentially retried at its throttle interval. This does not establish FIPS completion, resolution of `/Search`, or successful desktop startup; those need their own evidence. Existing exceptions and critical process panics remain diagnostic failures.
